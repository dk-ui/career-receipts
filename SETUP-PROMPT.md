# Career Vault — setup prompt

**For humans:** this file builds a private, AI-maintained record of your whole working life:
every job, project and degree, the files that prove what you did, and a CV where every number
traces back to evidence. Use it for reviews, promotion cases and job searches. It's the
no-clone version of this repository: the same vault, built from one prompt. Free to use, copy
and adapt (MIT).

**How to use it:**
1. Install [VS Code](https://code.visualstudio.com) and the **Claude Code** extension, or the
   Claude Code CLI. It runs on a Claude Pro or Max subscription. You don't need an API key.
2. Make an empty folder called `career-vault` in your **home folder**. Don't put it in
   Documents, Desktop, Downloads or anything synced to iCloud, OneDrive or Dropbox.
3. Open that folder in VS Code, open Claude Code, and paste everything below the line. Or save
   this file into the folder and say: *"Read SETUP-PROMPT.md and follow it."*

---

You are setting up a **career vault** for the person you're talking to (the **owner**). Build
the full structure below, then onboard them. They may not be technical. Use plain language,
say what each step is for before you run it, summarize command output instead of pasting it,
and ask before installing anything.

Work in this order: **Build (Part A) → Onboard (Part B) → Deepen later (Part C).** Every
step must be safe to re-run. Skip whatever already exists.

# What you're building, and why

A career vault is the owner's **single source of truth about their working life**. Most
people rewrite their resume from memory for every application, and numbers drift, get
inflated, or can't be defended when an interviewer asks "how do you know that?" The vault
fixes that with five ideas. Hold to all five in everything you build:

1. **One folder per chapter** of their working life (a job, degree, venture, freelance stint,
   volunteer role or major project), holding the story *and* the evidence.
2. **A claim with no artifact is a gap, not a fact.** Every chapter keeps a gap list and a
   status flag, so it's always visible what's proven and what isn't.
3. **Every number on the CV traces to an evidence ledger row**, with an honest status.
   Things remembered but undocumented are allowed, as long as they're labeled that way.
4. **Drop, don't sort.** The owner drops files into `inbox/`, and you file each one, rename it,
   describe it, close any gaps it proves, and empty the inbox.
5. **Mechanical gates, not good intentions.** A pre-commit check blocks ID numbers from
   entering history, and generators keep the indexes current. A rule that lives only in
   prose eventually gets skipped.

# Part A — Build the structure

## A1. Folder layout

```
career-vault/
├── CLAUDE.md               agent rules (A3); no frontmatter
├── README.md               the owner's front page (type: vault-root)
├── index.md                terse manifest of the root
├── START-HERE.md           plain-language guide for the owner
├── MANIFEST.md             GENERATED by tools/gen_manifest.py, never hand-edited
├── evidence-ledger.md      every claim on the CV → the file that proves it (A4)
├── cv.md                   the live CV (unless career-ops is installed, see Part C)
├── inbox/                  drop zone; contents gitignored; README.md + index.md tracked
├── profile/                who they are, what they want; photos/ for headshots
├── chapters/               one folder per chapter; README.md has the chapter table
│   └── <slug>/  README.md, index.md, media/
├── resumes/                every past resume version, YYYY-MM-<label>.<ext>
├── cover-letters/          every letter sent, YYYY-MM-DD-<company>.<ext>
├── job-search/             cv-last-sync.md (the CV as last built); tracker snapshot if career-ops
├── tools/                  privacy_scan.py, claims_check.py, add_frontmatter.py, gen_manifest.py,
│                           vault_integrity.py
│                           (README.md + index.md like every folder)
├── .githooks/              pre-commit, pre-push
└── .claude/skills/         file-inbox, add-chapter, sync-cv (and sync-career-ops if installed)
```

## A2. Documentation conventions (write these into CLAUDE.md as well)

- **Every folder gets two files.** `README.md` is the narrative: what's here, what's strong,
  what's missing. `index.md` is a terse manifest, one line per file or subfolder with a link
  and nothing narrative, so an agent can navigate cheaply. Read `index.md` first. A new folder
  gets both in the same change. The exceptions are `media/` and `profile/photos/`, whose files
  are listed in the parent's `index.md`.
- **Chapter READMEs** open with a status flag: ⚪ not started · 🔴 claims, no files yet ·
  🟡 partial · 🟢 strong. They end with a gap list of `- [ ]` items, each naming the
  kind of file that would prove the claim. When a filed artifact closes a gap, tick it **and
  re-judge the flag in the same change.** Describe flags to the owner as progress ("2 of 4
  proven"), never as a grade.
- **Descriptive file names:** `2024-q3-checkout-redesign-before-after.png`, never
  `IMG_4471.png`. Lowercase and hyphenated. Never overwrite; add `-2` instead.
- **Text matters more than the file.** Every artifact gets one or two lines in its chapter
  README saying what it shows and what it proves. A screenshot nobody described never gets
  found again.
- **Frontmatter.** Every `.md` except `CLAUDE.md`, `MANIFEST.md` and the inbox files starts
  with:
  ```yaml
  ---
  type: vault-root | chapter-readme | readme | manifest | doc
  updated: YYYY-MM-DD
  links: [relative/path.md]   # derived from body links by the tool; never hand-edited
  status: strong | partial | none | not-started   # chapter-readme only
  ---
  ```
  `type: manifest` is every `index.md`, `chapter-readme` is `chapters/<slug>/README.md`, and
  `readme` is any other README.

## A3. CLAUDE.md (the agent's rulebook)

Write `CLAUDE.md` so that any future session follows the system without this prompt. It
must cover:

- **First run.** If `profile/README.md` frontmatter says `status: not-set-up`, run Part B
  onboarding before anything else. "What's next" means do one item of Part C, then stop.
- **What this is.** The vault is the source of truth. Anything downstream (the live CV, a
  portfolio, a job-search tool) gets a distilled copy and never writes back silently.
- The layout table (A1), the conventions (A2) and the frontmatter contract.
- **Saving.** Git is the owner's undo button. Commit at the end of every task with a plain
  message (`file: offer letter → chapters/acme`). The only remote ever allowed is a
  **private** GitHub repo. Confirm with `gh repo view --json visibility -q .visibility` that it
  prints `PRIVATE` before adding or pushing to any remote. If `origin` exists, push at the end
  of each session.
- **Gates** (A6). Never use `--no-verify`. If the privacy gate blocks, fix the content.
- **Privacy.**
  - The vault never goes public.
  - Never file the raw form of an ID document: passport, driver's license, Social Security
    card, bank or pay statement with an account number, transcript with a student ID. The
    scanner can't read images or PDFs, so this is the agent's job. Extract what a CV needs
    ("B.S. Biology, State University, 2019"), tell the owner, and leave the original out.
    For an offer letter, record the role, dates and comp, not the document.
  - Named colleagues' quotes and contact details stay inside the vault unless the owner
    confirms that person agreed to be quoted.
  - Former employers' internal or NDA material gets a `> ⚠️ confidential — do not publish`
    line in its chapter README and never goes into a CV, portfolio or external tool.
- **Money.** Everything runs on the owner's Claude subscription. Never add an API key, and
  never run or schedule anything that calls a paid API, without the owner's explicit yes for
  that specific run. A general "set it up" is not a yes. Before a large batch job, say roughly
  how big it is.
- **Nothing is ever sent, submitted or posted for the owner.** Draft it, and they hit send.
- **Skills table:** `file-inbox`, `add-chapter`, `sync-cv`, and `sync-career-ops` if it's
  installed.

## A4. evidence-ledger.md

Explain who it's for, then define:

**What earns a row.** A fact becomes a claim when all three hold: (1) it will leave the vault
in a CV, cover letter, portfolio or interview answer; (2) someone could reasonably ask "how do
you know that?" (numbers, percentages, money, team sizes, superlatives like *first*, *only*,
*largest*); (3) being wrong would cost credibility. Tool lists, titles, dates and plain
descriptions of responsibilities don't need rows. `claims_check.py` enforces a cruder version:
**if a CV line has a digit, it needs a row.**

**Status key:**

| | Meaning |
|---|---|
| 🟢 SOURCED | A file in the vault shows the number |
| 🟡 DERIVED | Calculated or estimated from something documented. Fine to use if you can explain the math |
| 🔴 GAP | No file yet, but one could exist. Go find it. **Never used on a CV** |
| 🔵 SELF-ATTESTED | The owner's recollection, where the document stayed with the employer, or a number carried over from an old resume. Fine to use; be ready to say "from memory". Upgrade to 🟢 if a file turns up |

Then a table `| Claim | Evidence | Status |`, with one section per chapter, newest first.

## A5. Seed files

- **`profile/README.md`** (frontmatter `status: not-set-up`), with sections:
  - **Basics:** name as on the CV, location, current role and organization, remote / hybrid /
    on-site, relocation, email for work things, LinkedIn, portfolio
  - **What I'm using this for:** performance review, promotion case, job search, or just a
    record they trust, and when
  - **What I'm looking for (only if job searching):** roles and level, industries, salary
    floor and target, instant yes if…, deal-breakers
  - **What makes me different:** with a pointer to the chapter that proves it
  - **Photos:** points to `photos/`
  - A note that references name real people and are never quoted externally without their OK
- **`chapters/README.md`:** intro, the chapter table
  `| Chapter | Role | Dates | Evidence |` (newest first), and the flag legend. Note that
  plenty of jobs never produced a keepable file, which is what 🔵 is for.
- **Chapter template** at `.claude/skills/add-chapter/template/README.md`:
  ```
  # {Organization} — {Title}
  **Status: ⚪ not started** · {Mon YYYY} – {Mon YYYY or present} · {city / remote}
  {One or two sentences: what the organization does, what this role was for.}
  ## What I did        ← the long story; scope, team, what changed because they were there
  ## Highlights        ← the 2–4 things they'd lead with in a review or interview, each linked to proof or a gap
  ## Artifacts         ← | File | What it shows |
  ## Gaps              ← - [ ] {claim} — {what would prove it}
  ```
  Plus a matching `index.md` template.
- **`inbox/README.md`:** "Drop anything here and say *file my inbox*." List good things to
  drop (old resumes, cover letters, LinkedIn PDF, headshots, work screenshots, decks, kudos
  emails, reviews, certificates, reference letters). Say plainly: **don't drop ID documents
  or statements.** Explain that nothing here is saved to history until it's filed, so the
  folder should be empty between sessions.
- **`resumes/README.md`:** history, not the working copy. Old versions keep phrasing that
  worked and numbers they've since forgotten, but those numbers still need ledger rows before
  reuse.
- **`cover-letters/`, `job-search/`:** a short README and an index each.
- **`START-HERE.md`:** a one-page plain-language guide for the owner: what this is, the
  everyday phrases ("file my inbox", "sync my CV", "what's next"), the cost warning (never add
  an API key), the privacy warning (no ID documents, never make it public), and the one habit:
  *every number on your CV traces to a file*.
- **`README.md`:** the owner's front page, with a where-things-are table and the flag legend.
- **`.gitignore`:**
  ```
  inbox/*
  !inbox/README.md
  !inbox/index.md
  career-ops/
  .DS_Store
  __pycache__/
  node_modules/
  *.mov
  *.mp4
  *.m4v
  *.avi
  ```
  Videos are too large for git history. They're filed and described anyway, and the owner is
  told their only backup is a disk backup (Time Machine, File History or similar).

## A6. Tools and gates

Write five scripts in `tools/`. Use **Python 3 standard library only**. Each derives the
vault root from its own location (`Path(__file__).resolve().parent.parent`), never a
hardcoded path, and resolves files via `git ls-files` so that gitignored files never count as
existing. Keep each under ~250 lines, with a docstring explaining *why* it exists.

1. **`privacy_scan.py`** — the only **blocking** gate. A leak is the one mistake in this
   vault you can't fix by editing a file later, because once it's in history it needs a
   rewrite.
   - Modes: `--staged` (the staged versions of files, via `git show :path`) and `--all`
     (every tracked file).
   - Scans `.md .txt .csv .tsv .json .yml .yaml`. List files with `-z` so names with
     spaces or accents survive, and decode with `errors="replace"` so one odd byte can't
     crash the gate.
   - Rules:
     - US SSNs (`\b\d{3}-\d{2}-\d{4}\b`)
     - Card numbers: 13–19 digits with optional spaces or dashes that **pass a Luhn check**.
       The Luhn check keeps phone numbers and IDs from tripping it.
     - Labeled account, routing, passport, license and student-ID numbers (a label word,
       matched on a word boundary so "protein 120000" doesn't trip it, followed by an
       optional `no.`/`#`/`:` and a run of 5+ digits)
     - Masked or last-four forms (`****1234`, `xxxx1234`, and `card ending in 1234` when a <!-- privacy-scan: allow (quotes the pattern it describes) -->
       card or account word comes first, so "fiscal year ending 2024" doesn't trip it)
     - Dates of birth labeled `DOB` or `date of birth`
   - **Escape hatch:** a line containing `privacy-scan: allow` is skipped. Rule documents
     (CLAUDE.md, the tool itself) go in an `ALLOWLIST`.
   - Prints `file:line  reason` and **never the matched text** (the finding itself is the
     sensitive part). Exits 1 on any hit.
2. **`claims_check.py`** — **never blocks.** Reads the live CV (`career-ops/cv.md` if it
   exists, else `cv.md`). For each line containing a digit (ignoring dates, years and
   phone/email lines), checks whether `evidence-ledger.md` has a row containing that number.
   Lists unmatched lines, and lines whose number appears **only** in 🔴 rows (a 🔴 number
   never goes on a CV), then every ledger row still marked 🔴. If no CV exists yet, reports
   only the 🔴 rows. Exits 0 unless `--strict`. `--cv PATH` checks another CV against the
   ledger next to it.
3. **`add_frontmatter.py`** — **never blocks.** For every `.md` in the vault (excluding
   `CLAUDE.md`, `MANIFEST.md`, dot-folders, `career-ops/` and `inbox/`), adds the frontmatter block if it's missing,
   infers `type` from the path, sets `updated` from the file's last git commit date (or today
   if it's uncommitted), and **refreshes `links:` every run** from the body's relative
   markdown links to tracked `.md` files. Refreshing matters: insert-once leaves stale links
   behind forever. Preserves any other keys. Only rewrites files whose content changed.
4. **`gen_manifest.py`** — **never blocks** locally. Reads every `.md` **from the git index**
   (`git ls-files`, `git show :path`), not the disk, so the manifest describes what will be
   committed. Writes `MANIFEST.md`: a generated header warning not to hand-edit, then one
   line per folder that has a README, in tree order, with its status flag, open-gap count
   (`- [ ]` items) and type; then **dead links** (frontmatter `links:` entries that aren't
   tracked files); then **orphans** (files nothing links to, reported, never fatal).
   `--check` exits 1 if `MANIFEST.md` is stale or there are dead links. Without `--check`,
   it writes the file and exits 0.

5. **`vault_integrity.py`** — **never blocks**, and isn't in the hook. The reverse of a dead
   link: reports files on disk that no `index.md` registers (by link or `backtick` name),
   folders missing their README/index pair, and frontmatter-contract breaks. Files in
   `media/` and `profile/photos/` are registered in the parent folder's `index.md`. Skips
   `inbox/`. Run it after filing. `--strict` exits 1 on any finding.

**`.githooks/pre-commit`** (executable): run `privacy_scan.py --staged`, and abort the commit
if it fails. Then run `add_frontmatter.py`, re-stage only the `.md` files that were already staged
(never sweep in unrelated edits), **then** run `gen_manifest.py` (it reads the index, so the
refreshed `links:` must be staged first) and `git add MANIFEST.md`. Re-run the privacy scan on
what the generators produced. Then, only if `cv.md` or the ledger
is staged, run `claims_check.py` for information. Generator failures print a warning and
never block.

**`.githooks/pre-push`** (executable): if `gh` is installed and reports the remote isn't
`PRIVATE`, abort. Then run `privacy_scan.py --all`, and abort the push on any hit.

Activate with `git config core.hooksPath .githooks`. This is a local setting, so note in
CLAUDE.md that it must be re-run after any fresh clone.

## A7. Skills

Write each as `.claude/skills/<name>/SKILL.md` with `name:` and a `description:` in the
frontmatter that lists the phrases that should trigger it.

**`add-chapter`** — use when the owner mentions work that has no chapter yet.
1. Slug: lowercase, hyphenated, usually the organization (`acme`, `state-university`). If the
   same organization appears twice, suffix the role (`acme-intern`).
2. Copy the template into `chapters/<slug>/` and create `media/`. Fill in what's known, and
   write `?` for anything unknown. Never guess dates.
3. Put the owner's claims about the role in the gap list, and move the flag from ⚪ to 🔴.
4. Add a row to `chapters/README.md` (newest first) and a line to `chapters/index.md`.
5. Commit `add: <slug> chapter`.

**`file-inbox`** — use when `inbox/` isn't empty, the owner says "file my inbox", or they
share a file in chat. The promise: *they never need to know where anything goes, and the
vault never drifts because a file arrived without its paperwork.* For each file:
1. **Identify it.** Open it and read it. On macOS, convert `.docx`/`.pages`/`.rtf` with
   `textutil -convert txt -stdout`. Work out what it is, which chapter it belongs to (create
   one if none fits) and which claim or gap it proves. Ask **at most one question per batch**,
   and only when a wrong guess would be costly. Otherwise decide, and say what you assumed.
2. **Screen it** against the privacy rules: ID documents aren't filed (extract the facts
   instead); NDA material gets marked confidential; other people's details stay internal.
3. **File it:**

   | It is | Goes to |
   |---|---|
   | Resume (any version) | `resumes/YYYY-MM-<label>.<ext>`, dated by its content, not today |
   | Cover letter | `cover-letters/YYYY-MM-DD-<company>.<ext>` |
   | Headshot or personal photo | `profile/photos/` |
   | LinkedIn PDF, bio, certifications, references | `profile/` |
   | Work screenshot, sample, deck, award, review | `chapters/<slug>/` (images and video in `media/`) |

   Move with plain `mv`, since inbox files are untracked.
4. **Do the paperwork in the same change:** add a line to the destination `index.md`, write
   what the file shows in the README, **tick any gap it closes and re-judge the flag**, and
   add or upgrade an `evidence-ledger.md` row if it backs a number.
5. **Empty the inbox.** Commit `file: <what> → <where>`, and push if `origin` exists.
6. **Report in a few lines:** what went where, which gaps closed, what you left out and why.

**`sync-cv`** — use for "update my CV", "sync", or after new work is filed. Rebuilds `cv.md`
from the vault.
1. Read `profile/README.md`, every chapter README, the ledger, and the newest resume in
   `resumes/` (to match the owner's phrasing and section order).
2. Before overwriting, diff the current `cv.md` against `job-search/cv-last-sync.md`. If the
   owner hand-edited a fact, ask whether it's real and bring it into the vault before you
   rebuild. Never silently erase their edits.
3. Build it: Summary, Experience (newest first), Projects, Education, Skills.
   - **Every number comes from a ledger row.** 🟢 and 🟡 are used freely. 🔵 only if the
     owner keeps it. Never 🔴, never invented.
   - **Rephrase, don't embellish.** Never upgrade "helped with" to "led".
   - Leave NDA material out.
4. **Show, then write.** On the first build, give a summary. After that, show the diff (which
   bullets changed, which numbers came or went) and get a yes before writing.
5. Copy the result to `job-search/cv-last-sync.md`, then run `python3 tools/claims_check.py`
   and fix or drop every unsourced number.
6. Commit, and tell the owner what changed, any numbers you dropped, and the single most
   valuable 🔴 gap to go find.

## A8. Initialize

```bash
git init -b main
git config core.hooksPath .githooks
chmod +x .githooks/*
python3 tools/add_frontmatter.py && python3 tools/gen_manifest.py
python3 tools/privacy_scan.py --all
```

If git `user.name` or `user.email` isn't set, ask the owner and set it **for this repo
only**. Commit `chore: build career vault`. Then **self-test the gate:** stage a scratch file
containing `SSN 123-45-6789`, confirm the commit is blocked, then delete the file and unstage <!-- privacy-scan: allow (gate self-test fixture) -->
it. Tell the owner the gate works.

# Part B — Onboard (first session, ~15 minutes)

The goal of the first session is **a usable CV built honestly from what they already have**,
not a complete vault.

1. **Check the location.** Run `pwd`. If the path is inside Documents, Desktop, Downloads or
   a cloud-synced folder, stop. Explain that sync services can corrupt git history and that
   scheduled jobs often can't read those folders. Ask the owner to move the folder to their
   home folder and reopen it.
2. **Check prerequisites.** You need `git` and `python3`. On macOS, `xcode-select --install`
   provides both. Say what each is for before installing, and never install system software
   silently.
3. **Five questions, in one friendly message.** Write the answers into `profile/README.md`:
   1. Your name as you want it on your CV, and the email you use for work things
   2. Your current role and organization, and where you're based
   3. What do you want this for first: a performance review, a promotion case, a job search,
      or just a record you trust?
   4. If you're looking now or soon: what roles and level, and your salary floor? (Skip if not.)
   5. Anything you'd never take on again?
4. **Current resume.** "Drop your current resume into `inbox/`." Run `file-inbox`, then
   `sync-cv` in **fast-start mode:** build `cv.md` from the resume, and log every number on
   it in the ledger as 🔵 *self-attested, from resume YYYY-MM*. That's honest, and it keeps
   the claims check quiet. Rows upgrade to 🟢 as evidence arrives.
5. Set `profile/README.md` `status: active` and commit `chore: onboarding done`.
6. **Close with the habits:**
   - Drop files in `inbox/` → say "file my inbox"
   - Say "sync my CV" after adding work
   - Say "what's next" whenever you have 20 minutes
   - Nothing is ever sent for you

# Part C — Deepen (one item per "what's next", then stop)

Pick the first item not yet done, do only that one, and stop.

- **a. Work history.** "Walk me through your history, newest first: just organization,
  title and rough dates." Include freelance work, school, volunteering and side projects
  that matter. Run `add-chapter` for each. Then ask: "Which two or three things would you lead
  with in a review or an interview?" Those become highlights and gap-list items.
- **b. The big drop.** "Drop everything into the inbox: old resumes, cover letters, your
  LinkedIn PDF (Profile → More → Save to PDF), headshots, screenshots of your work, kudos
  emails, reviews. Don't sort anything. Skip IDs and statements." Run `file-inbox`, then
  `sync-cv`.
- **c. Private backup.**
  ```bash
  python3 tools/privacy_scan.py --all        # must be clean first
  gh auth login                              # the owner does this in a browser
  gh repo create career-vault --private --source . --push
  gh repo view --json visibility -q .visibility   # must print PRIVATE
  ```
  If the last command doesn't print `PRIVATE`, stop and fix that before anything else.
  Recommend a disk backup too, since it's the only copy of videos.
- **d. Review-ready.** Ask when their next review or promotion conversation is. Draft a
  one-page brag document from the chapters using only ledger-backed numbers. Nothing is sent
  for them.
- **e. Story depth.** Pick the weakest-evidence highlight in the ledger and question it
  the way an interviewer would: "How do you know it was 40%? What did the before look like?
  Who else was involved?" Write the answers into the chapter. This is interview prep.
- **f. Optional: the job-search engine.** Offer
  [career-ops](https://github.com/santifer/career-ops) (open source, MIT). It scans company
  job boards, scores postings against the owner, and tailors a CV for each one. It needs
  Node 18.17+.
  - Clone it into `career-ops/` inside the vault (already gitignored). Run `npm install`,
    then `node doctor.mjs --json --init-templates`.
  - From then on, the live CV is `career-ops/cv.md`. Write a `sync-career-ops` skill that
    **pulls back before it pushes:**
    - Fact corrections the owner made inside career-ops. Add a marked block to its
      `modes/_custom.md` telling it to log fact changes to `data/vault-corrections.md`.
    - Sent cover letters, copied into `cover-letters/`.
    - The tracker (`data/applications.md`), snapshotted into `job-search/`.
    - **Then** it rebuilds `cv.md` and `article-digest.md` from the vault using the
      `sync-cv` rules, and pre-fills its profile from `profile/README.md`.
  - Never commit inside career-ops. A weekly `node scan.mjs` makes plain web requests and
    uses no AI, so it's safe to schedule. **Never schedule evaluations**, because they spend
    the owner's plan every time.

When every item is done, say: "You're fully set up. Drop files in the inbox whenever you have
them, sync after you add work, and every number on your CV will always have an answer to
'how do you know that?'"
